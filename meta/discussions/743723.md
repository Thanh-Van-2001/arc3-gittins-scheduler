# Harness or model? Notes from a week of controlled harness experiments  (id 743723, votes None, by Sergei Makarov)

**Setting.** Over the past week we ran a series of controlled experiments on a public Duck-based harness. The model, the serving stack and the time budget stayed fixed. Each change was added as a single isolated layer and compared against the same baseline on the public games. We deliberately avoided stacking changes: when several layers ship together, a gain from one can hide a loss from another, and the combined result says little about either.

**Measurement.**The first result concerns the metric itself. Repeated runs of an identical build produce a wide spread of scores. The per-game outcome is close to bimodal: a game is either understood early or yields almost nothing. A single lucky or unlucky game can therefore move the aggregate noticeably. As a consequence, one run resolves only large effects. Reliable comparison requires the mean of several baseline runs, and many single-run "improvements" fall within the noise. We also found it useful to read the verdict on all games together and separately on the subset of games whose outcome is most stable. A change that only moves the volatile games is much harder to trust.

**Harness layers.** Almost every added layer scored at or below the baseline: consensus between sampled answers, a reasoning-discipline block, higher-resolution board images, and an executable world model with replay validation and search-based planning. Before reading any score, we checked that each layer had actually been active: its markers in the logs, and its traces in the model's tool calls. This step turned out to matter. The world-model scaffold is the clearest example: the model largely ignored it, so that run measured the presence of an unused instruction rather than the method. Offline, the model rarely produced a simulator that predicted unseen transitions better than a trivial "nothing changes" baseline. The comparison against that trivial baseline was important too: several simulators that looked exact on the observed transitions were no better than it on new ones.

**Where runs fail.**The most informative analysis compared stuck runs with successful runs of the same game. Replaying recorded runs on the local engine makes it possible to align them state by state. Both pass through the same states and diverge within the first few moves of a level. At most of these forks, the stuck run had already tried the action type that later proved decisive. The failure is therefore neither memory nor coverage of the action space. It is a judgement about the goal, formed early and then defended. Signals visible to the harness (repeated actions, stalled levels, move counts) predict this failure poorly at the moment it happens; they become clear only much later, when most of the budget is already spent. The same pattern has been described elsewhere on this forum as a "lottery effect."

**Interpretation.** A failure of early goal judgement sits inside the model rather than around it. Prompting and scaffolding change how the model spends its budget, but they barely change which hypothesis it commits to first. Once the harness is reasonably tuned, the remaining lever appears to be the model itself, or training that improves this judgement without memorizing particular games.

**Limitations.** All experiments used a single model and a single harness family, so the conclusions may not carry over to setups with a different model or a very different agent design. Public games are a small sample, and the relationship between public and hidden performance is itself noisy. Finally, "the layer did not help" here means "did not help beyond the noise in this configuration". It does not mean the underlying idea cannot work elsewhere.

--- Sergei Makarov (votes {'totalVotes': 1, 'canUpvote': True, 'totalUpvotes': 1}): A short follow-up with two numbers behind the claims in the post, since a few people asked how large the effects actually are.

Noise. Two runs of an identical build, one right after the other on the same server, with a 30-minute cap per game: 2.60 and 1.45, with the first level cleared in 15 games vs 9. Nothing differed between them except sampling. Over full-length runs of the same build we have seen a spread of roughly 4.5 to 9.4 on the public games. So a single run of a harness change tells you almost nothing unless the effect is very large. We now compare against the mean of several control runs, and we look at mechanism counters (requests per game, moves per request, calls that only inspect the board) before we look at the score.

The early fork. Aligning stuck runs with successful runs of the same game state by state, in 83% of the forks the stuck run had already tried the action type that later turned out to be decisive. It had the evidence; it drew the wrong conclusion about the goal and kept defending it. That is why we read the remaining gap as a judgement problem rather than an exploration or memory problem.

    --- Sergei Makarov (votes {'totalVotes': 1, 'canUpvote': True, 'totalUpvotes': 1}): Same here: dozens of small harness variants, and most of the signal drowns in run-to-run noise. One thing that has helped us with the GPU-time constraint is RunPod. It isn't free, but an RTX PRO 6000 (the same 96 GB card as the competition) is about 2.1/hour, and the Kaggle setup reproduces on it almost one-to-one: the same vLLM runtime dataset and model weights, the notebook cells executed as they are, and the public games played offline from the competition files.

A few things that saved us time, in case you try it:

Kaggle throttles downloads to roughly 40 MB/s per connection, so pulling the 119 GB model archive with several parallel range requests (and streaming it straight into the extractor) cuts the setup to about 15 minutes.
Start the vLLM server once and keep it alive between variants. Each 30-minute arm then costs ~32 minutes instead of ~45, and you can queue a whole batch of variants back to back.
Because every arm on the same pod shares the same server, the comparisons are cleaner than across separate Kaggle sessions. Even so, two identical control runs still differed a lot for us, so repeats are needed either way.
It's not a replacement for the real submission environment, but as extra "quota" for screening harness changes it has been well worth the cost for us.
